# Umi-OCR 启动与小文件优化建议

> 整理日期：2026-10-28。本文是待实施建议，不是构建、性能或验收通过记录。
>
> 已确认的方向：ZIP 使用 `ZIP_STORED`，只打包、不压缩；以减少小文件和改善拷贝、搬运及文件管理为目标，不把 ZIP 合并作为启动提速实验。启动优化独立进行，两条工作线最终组合验收。

## 1. 结论与范围

建议采用“**选择性聚合小文件 + 缩短首屏前同步路径 + 保持后端按需加载**”的组合方案，不做自解压单文件程序，不改模型、精度或依赖版本。

| 工作线 | 要解决的问题 | 主要手段 | 成功依据 |
| --- | --- | --- | --- |
| 小文件优化 | 程序目录文件多，拷贝、移动、展开安装和文件管理开销大 | 可兼容的 Python 文件聚合为 Stored ZIP；Qt 界面资源按需聚合为 RCC | 实际磁盘文件数、拷贝总耗时、打包与解包耗时、兼容性 |
| 启动优化 | 从启动到窗口可操作的等待较长 | 分段计时、减少同步导入、拆分初始化、延后非必要工作 | 同口径的窗口出现与首屏可操作时间，以及交互是否卡顿 |
| 首次识别体验 | worker、依赖、CUDA 和模型首次初始化较慢 | 保留懒加载；按用户选择在首屏就绪后预热、复用已有实例 | 首次识别时间、后续复用、资源占用和取消/退出行为 |

边界如下：

- “ZIP 只打包”指 `ZIP_STORED`，不是 Deflate 等压缩方式，也不是启动时先解压到临时目录。
- ZIP 优化不设置启动加速倍数目标，不以启动 A/B 测试证明它有价值；最终程序仍须通过正常启动和相关功能验证。
- 启动优化不能只让窗口提前出现，却把同样的长时间阻塞转移到第一次点击。
- 保留原有效配置、插件独立版本与 Host API 契约；不为本次优化统一升级各组件版本。
- 不减少 OCR 功能，不改模型权重、精度、输入保护边界或识别质量门禁。
- 本次交付仅为本文档；尚未实施上述代码和包结构变更。

## 3. 小文件方案：Stored ZIP + 原生文件外置

### 3.1 区分三层包装

| 层次 | 建议形式 | 是否展开 | 用途 |
| --- | --- | --- | --- |
| 安装后的运行时容器 | `app.zip`、`dependencies.zip`、插件私有 ZIP；界面可用 RCC | 兼容内容直接读取，不在启动时整体展开 | 降低长期磁盘文件数 |
| 可选的本地搬运包 | 整个干净程序目录的 Stored ZIP | 在目标位置展开外层；内层运行时容器继续保留 | 把整套程序作为一个文件复制或搬运 |
| 正式交付归档 | 保持项目规定的 `.tar.xz` | 用户安装时展开外层 | 现有正式交付、命名和版本保留契约 |

选择 ZIP 聚合小文件，不代表擅自把正式 Release 资产从 `.tar.xz` 改为 `.zip`。可选搬运包也不是必须长期保留的另一套正式资产。

如果只做“把现有散文件目录装进外层 ZIP，目标位置再全部展开”，收益主要发生在运输阶段，安装后的文件数不会减少。若要减少长期小文件，必须让兼容的内层容器在安装后继续保留。

### 3.2 建议布局

以下为逻辑示意，最终以逐包兼容性清单为准；不要求每个插件都生成所有容器。

```text
Umi-OCR/
├─ Umi-OCR.exe
├─ LICENSE、COPYING、LICENSES/       原样保留必要材料
├─ source/、source-snapshot.*        按现有对应源码契约保留
└─ UmiOCR-data/
   ├─ main.py                       保持轻量引导
   ├─ app.zip                       主程序兼容模块，ZIP_STORED
   ├─ dependencies.zip              宿主兼容依赖，ZIP_STORED
   ├─ ui.rcc                        适合聚合的 Qt 界面资源
   ├─ runtime/                      嵌入式 Python 原生运行时
   ├─ native/                       本项目原生组件
   ├─ site-packages/                原生扩展、必须外置的包和资源
   ├─ plugins/
   │  ├─ win32_PaddleOCRv6_CUDA/
   │  │  ├─ umi-plugin.json
   │  │  ├─ vendor.zip              仅已验证兼容的插件私有模块
   │  │  ├─ vendor/                 必须外置的依赖和原生文件
   │  │  └─ ...                     原模型与运行文件，布局按契约保留
   │  └─ win32_PaddleOCRVL_1_6/
   │     ├─ umi-plugin.json
   │     ├─ vendor.zip              仅已验证兼容的插件私有模块
   │     ├─ resources.rcc           仅在确有适用资源时采用
   │     └─ ...                     必须外置的代码、资源与模型
   └─ .settings、日志、任务临时目录  用户状态与可写数据，不装入只读容器
```

宿主、CUDA 和 PaddleVL 分开聚合，避免形成一个数 GB 的全局 ZIP。这样也可减少单个模块更新时需要重拷贝的范围。

### 3.3 可聚合与必须外置的内容

**可优先评估：**

- 无真实磁盘路径依赖的主程序纯 Python 模块。
- 不依赖文件枚举、原生加载和相邻数据文件的第三方纯 Python 模块。
- 已确认使用 Qt 资源访问方式的 QML、图标、图片等界面资源。

**默认保持外置，除非逐包验证证明另有安全做法：**

- `.dll`、`.pyd`、EXE 和其他原生运行文件。
- 模型权重及其按路径加载的配置、词表和配套文件。
- 依赖 `__file__`、`pathlib`、目录遍历、相邻文件或原生库搜索的包。
- 需要真实路径的数据资源、模板、字体、翻译、Qt 插件和 QML 运行时模块。
- 可写配置、日志、用户插件、任务文件、下载文件和用户自选模型路径。

不能只凭 `.py` 后缀决定可聚合，也不能只靠搜索 `__file__` 决定兼容。要同时检查资源 API、动态导入、包路径、元数据发现和实际功能。

不得无差别删除 `dist-info`、许可证、`.typed`、头文件、静态库或名为 `tests`、`examples` 的目录；如需裁剪，必须另有运行时闭包和来源依据，而不是按名称或后缀清理。

### 3.4 打包与加载规则

1. **不压缩、不自解压。** 所有运行时 ZIP 明确采用 `ZIP_STORED`，不加密、不分卷，不设置运行时整体解包后备路径。
2. **优先按包建立白名单。** 现有脚本的保留名单只能作为起点，不把“未命中保留名单”当作兼容证明。
3. **保持包命名空间和导入顺序。** 保留 `py_src` 等规范路径，避免散文件副本意外遮蔽 ZIP 内的新代码；必要的包初始化桥接文件例外，须明确记录。
4. **不混用插件依赖。** worker 私有 ZIP 仅由对应 worker 加载，不让 CUDA/VL 的依赖泄漏进宿主或其他插件。脚本写入 `worker_archives` 后，仍须确认实际 worker 正确读取，不能只写清单就认定生效。
5. **原源码可追溯。** 若容器包含 `.pyc`，同时保留与其对应的原始 `.py`，使用实际交付的 Python 工具链生成并核验；不借机改变优化级别或运行语义。
6. **避免隐式改写第三方代码。** 确需调整包搜索路径时，先评估已有桥接方式，记录原始文件、变更、补丁和许可要求，不静默修改上游初始化逻辑。
7. **资源路径单独验收。** RCC 需要验证相对 URL、动态组件、图片、插件页面、翻译、主题及文件选择行为；不能把“成功生成 RCC”当作界面兼容通过。
8. **可重现与完整性。** 固定容器成员顺序、规范路径和时间戳，拒绝重复/冲突成员、越界路径和链接，记录成员大小及 SHA-256；CRC 校验不能代替内容哈希和来源核验。

### 3.5 对现有脚本的处理

`merge_runtime.py` 会修改输入树、删除被合并的散文件并调整部分初始化文件，因此：

- 只允许在本次全新候选暂存目录内使用，不对固定安装、只读 seed、已冻结产品或历史候选原地运行。
- 先检查目标路径、链接边界和占用进程，再在构建阶段执行；不边运行边改包。
- 聚合发生在产品内容冻结之前；冻结之后不得重新运行脚本修补同一产品。
- 合并清单应说明每个文件进入哪个容器、哪些内容保留外置、是否发生源码或桥接变换。
- 检查现有正式核验器对 `app.zip` 的支持，并为第三方依赖、插件 ZIP 与 RCC 补齐对应的清单和来源核验；不得扩大“忽略差异”范围绕过门禁。

## 4. 启动方案：先测真实等待，再拆分同步路径

### 4.1 建立分段时间线

为正常启动记录以下节点，使用低开销计时，不在计时路径中执行全目录哈希或递归文件统计。

| 节点 | 含义 | 用途 |
| --- | --- | --- |
| S0 | 创建主程序进程 | 外部端到端起点 |
| S1 | Python 引导完成 | 判断运行时引导与初始导入开销 |
| S2 | Qt 应用与必要连接器准备完成 | 判断 Qt 和宿主导入开销 |
| S3 | 必要配置、插件元信息就绪 | 判断配置与发现阶段的同步开销 |
| S4 | 首帧显示 | 记录视觉上的启动完成点 |
| S5 | 当前页面可操作、必要命令入口就绪 | 作为首屏体验的主要指标 |
| S6 | 非必要后台初始化完成 | 防止“启动结束后仍长期阻塞”被隐藏 |

另行记录首次请求接纳、worker 就绪、CUDA/模型就绪和首个识别结果，不把这些节点混成一个“启动时间”。

进程内使用单调时钟；跨进程事件通过明确的请求/进程标识和统一观测方式关联，不拼接无法对齐的时间戳。窗口隐藏启动、托盘启动和 HTTP 就绪使用各自适用的完成条件，不能强行套用“可见窗口”。

### 4.2 首屏前只保留必要工作

**首屏前必须正确完成：**

- 单实例与命令行转发判定。
- 影响初始显示和可操作性的配置读取、语言、主题、缩放与窗口状态。
- 当前页面所需的连接器、必要能力选择和错误提示路径。
- 承诺为“就绪”的接口实际所需的路由与配置；不虚报 ready。

**优先计时并评估后移：**

- 只用于关于页或调试展示的详细硬件信息采集。
- 非当前页面的控制器、文档/二维码等重型依赖和完整设置控件树。
- 不影响当前可用性的额外插件详情、健康检查和服务状态查询。
- 重复的配置树转换、面板布局计算、主题/字体枚举和接口快照生成。

这些是待计时确认的候选点，不是已经证实的耗时根因。当前页面需要的状态不能为了缩短数字而删掉或延后到错误的位置。

### 4.3 真正分阶段，而不是只套一层延迟

- `Qt.callLater` 和短定时器只是改变执行时机，不会把重任务变成异步；回调仍可能阻塞 UI。
- 适合后台执行的文件 I/O、设备查询、轻量数据准备使用受控任务，结果通过信号回到主线程。
- QML、界面对象及有线程亲和性的 Qt 操作留在正确线程，不能为了提速任意搬到后台。
- 给每个阶段设置显式状态，处理取消、重试、退出和过期结果，避免启动完成后旧回调覆盖新配置。
- 不产生“后台初始化尚未完成但按钮已放行”的竞态；必要时仅禁用受影响的入口，并展示准确状态。

### 4.4 延续现有懒加载与缓存

- 插件发现继续以清单和轻量配置为主，不在发现阶段导入 Paddle、CUDA 或启动全部 worker。
- 设置项的数据定义与控件实例化分离；已有 `lazyPanel` 保留，针对剩余重复构造做优化。
- 只导入当前真正需要的页面实现，检查启动连接器是否经间接导入拉入未使用的重型模块。
- 复用已有的后端实例、插件配置快照和合适的 Qt 缓存，不重复创建同等实例。
- 若增加缓存，必须有明确的失效条件，覆盖插件启停、清单/配置变化、语言和主题变化；不能让缓存把旧状态长期保留。
- 首轮不引入新的 AOT、Nuitka、定制解释器或依赖升级；只有现有路径不足且证据明确时，才讨论更大的架构变化。

## 5. 首次识别与预热策略

保留“默认按需加载，用户可选择后台预热”的方向，不静默改写已有有效设置。

- 立即预热也应在首屏必要状态就绪后调度，避免与 QML 初始化抢占磁盘、CPU 和显存。
- 延迟预热使用现有设置和生命周期契约，明确等待、执行、失败与取消状态。
- GUI、HTTP、手动预热和自动预热继续遵守既有重型执行槽与实例复用规则，不各建一份模型或同时预热多个重型后端。
- 用户发起真实任务时，不因后台准备造成重复加载；任务与预热的优先级和互斥关系须可验证。
- 内存/显存紧张、用户关闭预热、切换后端或正常退出时，正确停止尚未需要的准备工作，不自行终止用户进程。
- 分别报告首屏时间、首次识别时间与预热资源成本，不能只展示有利的一项。

预热是在时间与资源之间做取舍，不是消除模型加载成本；本轮不以量化、改权重或放宽保护边界替代启动优化。

## 6. 验证与比较方法

### 6.1 小文件优化的评价方式

**不安排以 ZIP 提升启动速度为目的的 A/B 测试。** 针对文件布局，记录以下指标：

| 指标 | 记录要求 |
| --- | --- |
| 磁盘文件总数与小文件数 | 分别统计宿主、各插件、源码/许可和完整安装；ZIP 内成员数不计为磁盘文件数，但另列成员清单 |
| 逻辑大小与占用空间 | 区分原始内容大小、容器大小与文件系统分配空间，不把减少分配开销说成内容被压缩 |
| 候选生成耗时 | 记录打包、校验成本，不能只比较已经生成的单个 ZIP 的复制时间 |
| 完整搬运耗时 | 区分直接复制运行目录、复制外层搬运包并展开、展开正式归档等不同流程，不混为一项 |
| 增量更新成本 | 记录小改动需要重拷贝多少容器，防止减少文件数却明显放大更新量 |
| 兼容性与恢复 | 验证导入、资源访问和正常错误提示；损坏容器应明确失败，不静默解包或换用旧散文件 |

选择实际使用场景，例如本机磁盘、移动存储或网络共享；记录源/目标介质、文件系统、系统状态和测试输入。杀毒软件保持正常开启，不能把不一致的扫描或缓存状态造成的差异当作稳定收益。

完整复制数 GB 的模型可能掩盖代码小文件的差异。可以同时记录“代码/资源部分”和“完整安装”，但子集结果不能宣称为整套程序的收益。重复轮次应结合可用磁盘空间与写入成本确定，不无意义地反复复制模型。

打包和解包会新增本地读写；单次本机复制未必更快，实测无收益也应如实保留。只要文件数、搬运便利性和兼容性满足目标，也可以接受“没有明确的端到端速度提升”。

### 6.2 启动优化的评价方式

- 使用同一机器、同一用户配置、同一模型与依赖、同一窗口/预热策略。
- 在相同包布局下比较启动逻辑改动，避免把 ZIP 合并混入归因。
- 分别报告明确条件下的冷启动和重复启动，不把预热后的多次启动称为冷启动。
- 记录原始样本、重复次数、中位数及离散情况；重复次数不足时不作强统计结论。
- 以首屏可操作为主，同时检查首次点击、拖入文件和必要命令入口是否仍有明显长阻塞。
- 后台任务不得与正式计时并行执行无关构建、哈希或模型测试；无法隔离时注明干扰。
- 不例行清空系统缓存、关闭安全软件或改变全局系统设置。

已有 [启动基准脚本](../benchmarks/benchmark_startup_ui.py) 可参考其窗口观测思路，但它会临时清理便携配置并强制结束被测进程，**不原样用于当前固定安装**。应先调整为隔离状态、明确就绪节点和正常退出的测量方式。

### 6.3 最小功能回归矩阵

按实际改动选择最小覆盖集合，不因为打包就例行重跑所有历史测试。

| 改动范围 | 必须覆盖的直接行为 |
| --- | --- |
| 主程序 Python 聚合或导入调整 | 模块来源正确、动态导入、单实例/CLI、设置读写、异常报告与正常退出 |
| Qt 资源聚合或界面初始化调整 | 首屏可操作、当前页、设置懒创建、主题/语言/缩放、图标图片、动态 QML 与插件页 |
| 宿主依赖聚合 | 涉及包的原生加载、资源与元数据查找，以及直接使用它们的功能冒烟 |
| 插件私有依赖聚合 | 对应 worker 的真实导入、原生依赖解析、必要的模型初始化、代表性功能请求和正常释放 |
| 预热与生命周期调整 | 按需/立即/延迟预热、真实任务与预热互斥复用、后端切换、失败、取消和退出 |
| 接口启动时序调整 | 实际 CLI/HTTP 接纳、路由、能力配置就绪，以及启动中请求的明确行为 |
| 最终组合 | 从实际候选归档全新重装，验证宿主与已变更插件共同工作，无旧目录或系统依赖兜底 |

未触及的识别算法、模型质量矩阵、HDR 捕获或其他无关路径不例行全量重跑。若共享底层或资源路径的变化扩大了风险，先说明原因再扩展定向覆盖；正式交付要求中的必需项目仍须满足。

## 7. 建议实施顺序

### 阶段 A：建立可追溯基线

- 固定源码、基线程序、配置和组件身份，不假定现有安装就是最新源码。
- 建立正常启动的分段观测，记录首屏与首次识别的独立基线。
- 建立候选聚合白名单和搬运场景，确认源/目标容量与临时工作范围。

产出：分段原始记录、瓶颈归因、文件清单与明确的改动范围。

### 阶段 B：低风险启动逻辑优化

- 先处理已测出的非必要同步工作与重复构造。
- 保留必要状态，补齐异步结果、错误、退出和配置失效边界。
- 在包布局不变的条件下验证启动体验，防止错误归因。

产出：独立代码变更、同口径启动比较和受影响功能回归结果。

### 阶段 C：宿主小文件聚合

- 在全新候选目录生成 `app.zip`、兼容的依赖 ZIP；RCC 仅在资源访问验证明确后接入。
- 接入构建清单与来源核验，保证内容冻结前完成所有变换。
- 检查实际文件数、搬运成本和功能兼容，不要求证明 ZIP 提升启动速度。

产出：宿主候选、容器成员清单、前后布局统计和兼容性结果。

### 阶段 D：按授权范围聚合插件

- CUDA 与 PaddleVL 分开评估、分开构建，只处理有变更的组件。
- 插件变更在用户授权的对应插件项目内进行；不因宿主方案而取得兄弟项目的写入或清理授权。
- 检查 worker 私有路径和模型资源查找，不能仅因宿主 ZIP 可用就认定插件也兼容。

产出：实际变更插件的独立候选、清单、定向运行结果和未验收限制。

### 阶段 E：组合、重装与交付审查

- 用本轮实际候选和可复用的已核验未变更组件，生成具名组合。
- 从实际最终归档在全新暂存目录重装，再验证组合可用性。
- 给出程序、文案、性能与搬运结果、未验收限制和清理预演，交用户审查。

不预设“必须减少到几百个文件”或“必须快几倍”。目标是有真实收益、功能不退化、来源可追溯；不兼容或收益不足的聚合项可以保持外置，并记录原因。

## 8. 构建、交付与清理约束

执行工作目录限定在本项目内，例如 `build/audit/startup-small-files-<运行标识>/`；构建和重装使用本次全新目录，最终路径以实际具名记录为准，不在用户主目录或 release 顶层散放临时材料。

- 主程序、CUDA、PaddleVL 独立维护版本和候选身份；只构建有变更的组件，不为版本号对齐重编未变更组件。
- 不更换 Python、Qt、Paddle、CUDA 依赖锁，不下载/量化/修改模型，不将改精度包装成启动优化。
- 运行时布局变换、对应源码、许可证、补丁、清单与归档必须匹配。聚合源码不等于可以省略产品内部必需的源码和许可材料。
- 已冻结产品不原地刷新；新验证不能回写成旧候选、旧归档或旧源码的历史 PASS。
- 若复用未改动组件或历史验证，注明其身份、来源、适用范围、不变依据和本次未执行项。
- 不覆盖当前固定安装。后续确需更新时，遵守先全新重装核验、再检查占用与用户数据、最后切换固定目录的项目规则。
- 删除或替换前核对具体目标、理由、保留项、活动进程及链接边界；有占用时要求用户正常退出，不自行杀进程，不绕过权限拒绝。
- 不清理插件项目、未知缓存、模型、用户配置、任务数据和历史审计证据；不运行旧清理脚本。
- 正式 release 继续遵守各组件最新版本与紧邻上一版本的 `.tar.xz` 保留规则；性能报告、搬运测试和工作清单放在 `build/audit` 等工作目录。
- 必须等待用户对当次实际程序和 Release 文案明确同意，才推送 GitHub 的 main、标签或 Release；认可本文档不能代替当次交付审查。

## 9. 后续实际实施的交付清单

1. 源码变更与对应组件身份：哪些改启动逻辑，哪些只改包结构，哪些保持不变。
2. 可兼容聚合白名单、外置保留清单，以及未聚合的原因。
3. 每个 ZIP/RCC 的内容清单、成员哈希、容器哈希和必要的变换记录。
4. 文件数量、大小/占用空间、打包与搬运测试原始结果及适用条件。
5. 独立的启动分段原始记录、首屏可操作比较及首次识别/预热资源结果。
6. 受影响功能的定向验证、包内运行和最终归档重装记录。
7. 实际候选程序与 Release 文案、未验收限制及本项目清理预演。
8. 主要保留项、已删除临时项和清理结果；有阻塞时如实保留，不强删。

## 10. 最终建议

**采用 Stored ZIP 选择性聚合小文件，Qt 资源按兼容性采用 RCC，原生依赖、模型和用户状态保持外置；不做自解压、不改变现有正式归档格式。**

**启动速度通过独立计时、减少非必要同步工作、改进懒加载与预热调度来优化。ZIP 不承担启动提速承诺，但最终组合仍须正确启动、工作和退出。**

本方案不依赖删除源码许可证、关闭安全软件、变更模型精度或突破发布门禁来获得表面上的改善。
