# PP-OCRv6 CUDA 设置说明

Umi-OCR 3.0.0 面向 Windows 10/11 x64。基础包可独立运行；PP-OCRv6 CUDA 是单独安装的插件，与基础包共用 Python 3.13 运行时。该插件使用 NVIDIA CUDA 12.6 PaddlePaddle GPU，不提供 CPU、oneDNN、ONNX 或 DirectML 推理后端，也不会在 CUDA 失败时回退到 CPU。插件相关协助：[QQ 联系群](https://qm.qq.com/q/5XHoXCOU26)。

界面语言与 OCR 识别语言是两件事。界面仍可切换中文、英语、日语等语言；PP-OCRv6_medium 使用统一的多语言识别能力，因此当前 CUDA 插件不提供“识别语言/语言包”设置。

## 预设

只有用户主动选择预设时，预设才会覆盖受管参数。手动修改检测模型、识别模型、方向、去扭曲、文本行方向、长边、批量大小或阈值中的任一项后，预设立即显示为“自定义”。程序不会静默恢复预设值。

| 预设 | 模型 | 辅助阶段 | 长边 | 识别批量 | 阈值 | 适用场景与资源影响 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 速度优先 | medium | 全部关闭 | 1600 px | 16 | 0.60 | 降低耗时和显存；小字、旋转或拍照文档质量可能下降。 |
| 均衡 | medium | 文档方向和文本行方向开启；去扭曲按任务 | 2560 px | 12 | 0.50 | 在质量、耗时和内存间折中。 |
| 高精度（默认） | medium | 全部适用辅助阶段；去扭曲按任务 | 4000 px | 6 | 0.45 | 提高小字、旋转、透视和低对比内容质量；增加耗时、显存和内存。 |

“按任务去扭曲”在普通截图 OCR 中关闭，在批量图片和渲染文档 OCR 中开启。用户可明确改为“关闭”或“启用”。

## OCR 选项

| 短名称 | 默认值 | 作用 | 质量、耗时与资源影响 |
| --- | --- | --- | --- |
| 文字检测模型 | `PP-OCRv6_medium` | 定位图片中的文字区域。 | medium 提高小字、密集排版和复杂背景质量，但比小模型增加耗时、显存和内存。本发行包没有其他模型可选。 |
| 文字识别模型 | `PP-OCRv6_medium` | 将文字区域转换为字符。 | medium 提高字符准确率和统一多语言表现，但增加耗时、显存和内存。本发行包没有其他模型可选。 |
| 文档方向分类 | 启用 | 自动旋转横放或倒置文档。 | 提高方向错误文档的质量；增加少量处理时间和显存。 |
| 文档去扭曲 | 按任务自动 | 校正拍照扫描件的弯曲、透视或褶皱。 | 提高书页和手机拍摄内容质量；增加耗时、显存和内存。普通截图关闭可提速。 |
| 文本行方向分类 | 启用 | 校正单独旋转的文字行。 | 提高海报、标签和复杂排版质量；增加耗时和显存。 |
| 长边限制 | 4000 px | 在检测前限制输入图像长边。 | 提高数值可改善大图小字质量，但增加耗时、显存和内存；降低数值可提速。 |
| 识别批量大小 | 6 | 一次送入识别模型的文本行数量。 | 提高数值可降低大量文本行的总耗时，但增加显存和内存；显存不足时降低。 |
| 置信度阈值 | 0.45 | 丢弃低置信度识别结果。 | 提高可减少误识别并略降后处理耗时，但可能漏掉低对比文字；降低会保留更多候选。 |

## 硬件与预处理

| 短名称 | 默认值 | 作用与资源影响 |
| --- | --- | --- |
| 推理加速 | NVIDIA CUDA 12.6（必需） | 固定为 GPU 推理。CUDA 不可用时 OCR 明确失败；没有 CPU、oneDNN、ONNX 或 DirectML 选项。 |
| CUDA 设备 | `gpu:0` | 用 `gpu:N` 选择 NVIDIA 显卡。所有 Paddle 模型都显式使用该设备，模型和中间张量占用该卡显存。 |
| 预处理线程 | 逻辑核心少于 6 时使用全部，否则为逻辑核心数减 4 | 只控制 OpenCV/Python 图像解码和预处理。增加线程可降低预处理耗时，也会增加 CPU 与内存占用；它不代表 CPU 推理。 |

NVIDIA Windows 驱动最低版本为 `560.76`。建议使用更新的稳定驱动。CUDA 初始化失败时 Umi-OCR 主程序、设置和二维码功能仍可使用，但截图、批量、PDF 和 HTTP/CLI 的 Paddle OCR 任务会返回明确错误。

## 预热、驻留与清理

主窗口首帧完成后，程序才会按下列全局设置加载模型，不在首屏之前导入 Paddle、OpenCV、NumPy、Pillow 或 PyMuPDF，也不会创建命令行窗口。首次预热包含 CUDA 上下文、模型反序列化和内核初始化，因此仍明显慢于后续识别。

| 设置 | 默认值 | 用途与资源影响 |
| --- | --- | --- |
| 模型预热 | 首次使用时加载 | 默认不在启动后提前占用资源，首次 OCR 时再加载；选择延迟预热可在后台提前加载，以降低首次 OCR 等待。 |
| 预热延迟 | 0 分钟 | 范围 `0–60` 分钟，仅用于延迟预热；0 表示首帧后立即后台加载。 |
| 自动清理模型 | 不自动清理 | 可改为系统内存占用超过 90% 时每 6 分钟检查，或无使用时自动清理。OCR 任务运行期间绝不清理。 |
| 无使用清理时间 | 30 分钟 | 范围 `5–120` 分钟；从最后一次 OCR 使用后计时。清理可降低显存和内存占用，但下次识别需要重新加载。 |

托盘右键菜单把“预热 OCR 模型”和“清理 OCR 后台”合并为一个动态操作：未加载时预热，加载后清理，预热过程中禁用。手动清理只在没有 OCR 任务时执行。

成功加载后，Paddle 引擎和模型保持在所选 `gpu:N` 上并供截图任务复用。批量图片与文档任务在有效辅助阶段相同时复用同一引擎；只有去扭曲或文本行方向等有效流水线发生变化时才重建。Python、OpenCV、解码缓冲和模型元数据仍会占用系统内存，并不表示发生了 CPU 推理。清理会关闭 PaddleOCR、回收 Python 对象并请求释放 Paddle CUDA 缓存；修改 CUDA 设备或 OCR 全局设置会在活动任务结束后自动切换并释放旧引擎；退出程序会结束工作进程。

## 图片输入格式

截图、批量图片、HTTP Base64 和 CLI 路径调用共用同一解码入口。支持 `JPEG`、`PNG`、`AVIF`、`WebP`、`JPEG XL`、`JPEG XR/WDP/HDP`、`BMP` 和 `TIFF`。

- AVIF 强制使用 Pillow/libavif 的 dav1d 解码器；dav1d 不可用时拒绝解码，不静默换用其他 AV1 解码器。
- WebP 优先使用 OpenCV/libwebp。
- JPEG XL 和 JPEG XR 使用 imagecodecs 的 libjxl/jxrlib。
- EXIF 方向会在 OCR 前应用；透明像素与白色背景合成；10/12/16-bit 输入会确定性转换为连续 BGR `uint8`。

## HDR 截图校准

“HDR SDR 白点”和“HDR 峰值亮度”的默认值都是 `0`，表示分别读取 Windows SDR white 与 DXGI 峰值。手动提高 SDR 白点会改变整体映射亮度；峰值设得过高会压缩更多高光，设得过低会丢失层次。只有在真实 HDR 测试图上确认系统数据错误时才覆盖，步骤见 [HDR 测试与校准](HDR_TEST_WINDOWS.md)。
