## 二、大图与资源预算

### 已核对的设备与历史证据

本机本轮只读查询结果：

| 项目 | 结果 |
| --- | --- |
| 显卡 | RTX 4060 Laptop GPU |
| 显存 | 8188 MiB |
| 物理内存 | 33,736,024,064 B，约 31.4 GiB |
| 本机 llama.cpp 源码 | `74bca3950054eed1795f525cb9cf06bfe796492d` |
| 当前 llama.cpp 构建 Toolkit | CMakeCache 记录 13.4.92 |

因此“8G”暂按显存分析，不把它当作本机物理内存。若用户要求兼容只有 8 GB 系统 RAM 的其他机器，需要单独设置验收条件。

当前固定安装目录内 PaddleVL 清单的实际插件版本是 3.0.0；模型名称中的 1.6 不是插件版本。定点核对其已安装源码，未修改安装目录：

| 参数或行为 | 当前实现 |
| --- | --- |
| 服务默认上下文 / 槽数 | 8192 / 1 |
| 默认最大输出 | 4096 token，服务层和识别层各有配置 |
| 服务默认视觉参数 | 2048 token |
| spotting 图像像素预算 | 固定 min 112896、max 1605632 |
| spotting 处理方式 | 整图、关闭版面检测，没有自动分块 |
| 请求 / 启动默认超时 | 120 / 180 秒 |

`worker.py` 的 spotting 调用显式固定像素预算，因此仅提高服务的视觉 token 参数，不会同步提高它。密集长图可能缩到文字不可读，输出还要容纳文字与定位坐标；这属于有代码证据的风险，不等于已经复现用户这张图的根因。

2026-10-25 的 `build/audit/20261025-paddlevl-local-r1/real-paddlevl.json` 记录过单请求 PaddleVL 服务启动和文档结果，启动参数包括上下文 8192、输出上限 4096、并发槽 1、视觉 token 参数 2048。该记录不能证明当前失败大图可识别，也不能证明 2048 参数对当前 llama.cpp 的 PaddleOCR 分支真正生效。

旧 `build/audit/performance-summary.json` 是 2.8.1 的性能材料，记录的整卡占用包含其他应用。它既不是当前模型的净占用，也不是本轮新测数据，不据此承诺最高上下文。

### 上下文不等于可接受的整图大小

必须同时约束：图片完整解码占用、缩放后的文字可读性、视觉 token、输入提示、输出文字与定位坐标、KV 缓存、视觉图计算临时缓冲，以及同卡其他模型。

对 PaddleOCR-VL 而言，文字定位输出还包含坐标。图很密时，即使文本本身能放下，定位输出也可能超过生成预算。超长图应评估有重叠的分块、原图坐标回映射和边缘去重；文档应按版面区域处理，而不是一律把整页压成小图。重试仅针对明确可恢复的失败，不能无限重试或静默输出不完整结果。

传统 PP-OCR 不使用语言模型上下文。其限制主要是解码、检测输入尺寸、检测/识别计算和内存，不应给它强加一个假的“上下文长度”设置。

当前 CUDA 插件先用 OpenCV 完整解码，再由检测模型限制长边；默认长边 4000 并非原图总像素或解码内存上限。其推理等待固定为 180 秒，适配器没有大图分块或自动资源降档。PaddleVL 的宿主请求默认等待 120 秒，progress 不会重置等待时限；spotting 的内部 HTTP 客户端也未像 document 那样显式注入相同的超时和重试参数。

完整 PaddleVL 文档模式还有独立风险：先把整份预测结果收集为列表，再按 pageRange 裁切。因此选少数页不等于只推理这些页；逐区域重试也受整份请求的超时限制。应在输入阶段选择页、逐页回传并保留部分结果，而不是先推完整份再筛选。

界面错误不会画在图片叠加层上。无字结果不绘框，推理错误主要进入记录和通知。复现时应查看该条记录的状态码、执行模型、错误、警告和耗时，不能只看“文字”开关是否开启。

### PaddleOCR-VL 的理论值与待验证档位

官方 config.json 声明最大位置长度 131072，不等于任何 8 GB 显卡都能稳定使用该长度。根据该配置的 18 层、2 个 KV 头、每头 128 维，假设 K/V 都为 F16 且一个完整槽，纯 KV 理论占用如下：

| 上下文 token | 纯 KV 理论占用 | 本轮建议定位 |
| --- | --- | --- |
| 8192 | 144 MiB | 保守兼容起点，已有历史服务参数记录 |
| 16384 | 288 MiB | 首选扩容验证档，不作为已通过默认 |
| 32768 | 576 MiB | 高密度输入候选档，须测完整 Pipeline 峰值和输出时间 |
| 65536 | 1152 MiB | 不建议直接作为普通用户默认 |
| 131072 | 2304 MiB | 仅架构声明上限，不能宣称 8 GB 整机已验收 |

计算式：层数 × K/V 两份 × KV 头数 × 每头维度 × 每元素字节数 × token 数。上述数值不含权重、视觉编码器、计算缓冲、槽管理开销、桌面占用与版面检测模型。

输入与输出共享上下文预算，且受单次最大生成数限制。不能承诺“8192 上下文可输入 8192 个汉字”。图像 token 不是像素数，也不是汉字数。密集截图能承受多少内容，必须以视觉预算、实际输出长度、耗时和峰值为准。

建议在现有精度下先验证单槽 8192/16384/32768、短截图/密集截图/长图/复杂文档、单模型及切换后的资源回收，再决定最终默认和上限。不在这轮评估中擅自量化或改变模型精度。

### 本机 llama.cpp 的视觉预算注意事项

本机 `tools/mtmd/clip.cpp` 的 PaddleOCR 初始化分支读取 GGUF 中的 min/max pixels，并设置预热预算。该分支没有调用同文件其他模型使用的 `set_limit_image_tokens()` 来应用自定义视觉 token 上限。`clip-model.h` 的预热方法会参考自定义上限，但这不等同于实际推理像素限制已被覆盖。

因此存在明确的静态风险：命令行和设置界面接受 `--image-max-tokens`，不代表 PaddleOCR 实际视觉输入已按该值改变。实施前应核对加载日志与真实 image token 数；如需要修改 llama.cpp，应在独立构建目录固定提交、保留补丁并做针对性验证。不能只把上下文或视觉预算数字调大就宣布大图问题解决。

## 三、HTTP 能力边界

主程序现有图片接口走全局 `MissionOCR`。旧文档接口走 `MissionDOC`，分页渲染或提图后再交给同一个 OCR 后端；它没有调用结构化 `MissionDocument`。

固定安装目录的 PaddleVL 3.0.0 清单声明了 OCR 与 document 两种能力，spotting worker 可提供文字和多边形。当前宿主图片接口可以使用已经选中的这一 OCR 能力，但不能据此宣称旧文档接口已拥有另一 document 能力的结构化输出。

| 能力 | 静态链路判断 | 本轮实测 |
| --- | --- | --- |
| 当前已选 CUDA 后端识别图片 | 可达，仍取决于插件就绪与输入支持 | 未执行 |
| 当前已选且声明 OCR 能力的 PaddleVL 识别图片 | 宿主可达；实际 spotting 限制须核对插件 | 未执行 |
| 旧文档接口逐页 OCR | 可达当前 OCR 后端 | 未执行 |
| 每请求独立选择 CUDA / PaddleVL 插件 | 现有路由不完整，普通 options 键不会自动切插件 | 未执行 |
| PaddleVL 完整文档解析、结构化结果与资源 | 现有旧文档路由不提供同等能力 | 未执行 |

若完善 API，建议保留旧接口兼容，同时增加显式模型标识与结构化文档任务协议。至少要定义能力查询、参数校验、任务状态、取消、错误分类和资源取回。不能通过请求中随意改全局模型，干扰正在进行的 GUI 任务。

现有通用 API 未按插件 schema 完成所有数值、枚举和未知键校验，GUI 的范围不自动成为 HTTP 的范围。资源预算校验应放在服务端真实执行边界，不能只靠控件最小/最大值。

## 四、llama.cpp 分发与 NVIDIA 兼容

### 分发建议

llama.cpp 采用 MIT License，允许符合条款的再分发，应附版权与许可。Windows 运行时还需核对实际 DLL、第三方许可和 Microsoft 运行库要求；CUDA 组件仅按对应版本协议列出的 redistributable 范围附带，不复制整个 Toolkit 或显卡驱动。

PaddlePaddle 官方 GGUF 页面声明 Apache-2.0；模型包仍需按最终选定文件和版本核对许可证、NOTICE、来源、修改记录和哈希。这不是“已获所有权利授权”的声明。模型主 GGUF 与视觉投影 mmproj 必须匹配，不能让用户只下载前者就宣称已可 OCR。

推荐第一阶段：PaddleVL 插件附固定版本 llama.cpp 运行时，提供模型导入与完整性/配对校验。保留高级外部服务连接，不强制依赖用户安装完整 CUDA Toolkit。完整离线模型包作为明确确认后的交付选择；本轮没有下载或分发任何模型。

### GTX 10 系起的兼容目标

NVIDIA 官方 CUDA 13.0 发布说明明确移除了 Maxwell、Pascal、Volta 的离线编译与库支持。GTX 10 系通常属 Pascal，不能用当前 CUDA 13 构建承诺支持。

本机 CMakeCache 与 build.ninja 显示 CUDA 13.4.92，目标包含 75、80、86、89、90、120a、121a，未包含 Pascal 的 61。因此现有产物不满足用户所述兼容目标。

可行工程路径是评估 CUDA 12.9 的多架构兼容构建，或提供兼容分支与现代分支并自动选择。应显式固定 GPU 架构而不是 native，并逐一核对 CUDA 库、驱动最低版本、PaddleOCR-VL 算子和显存容量。新架构还会继续出现，不能承诺覆盖所有未来 NVIDIA GPU。

llama.cpp 的兼容性不等于 PP-OCR CUDA 插件的兼容性。后者依赖自己的 PaddlePaddle/CUDA 构建，若“10 系起”也包括它，需要另列验证矩阵。

本机只能做 RTX 4060 实机验收。Pascal/Turing/Ampere/Blackwell 等其他设备须由对应硬件验证，不能把编译包含了某个架构当作整套 OCR 已运行通过。

## 五、共享设置与实施边界

### 推荐内部结构

- 展示树与持久化键分离。移动 PaddleVL 服务控件时，优先保留 `pluginServices.<pluginId>.<serviceId>.*` 规范键，避免只挪 UI 就丢失路径和端口配置。
- 保留一份全局生命周期策略，并为传统 PP-OCR worker 与 PaddleVL 共享服务各写适配。延时预热、闲置清理、内存不足清理需要明确相同语义。
- PaddleVL 清理以活动租约、等待请求和自有进程为门禁。OCR 空闲而文档任务仍忙时不得退出服务；外部服务不得被软件擅自关闭。
- 模型专属参数仍按实际页面和后端持久化，避免切换后相互污染；共享策略则从同一来源读写，多窗口保持同步。
- 当前模型切换是全局单例，任务中会拒绝切换。推荐先保留这一语义，让多个页面都能操作同一个模型选择。若要求不同页面各自选模型并可并行，应改任务路由、实例管理和资源调度，不是仅增加下拉框。
- 修复现有预热取值前缀不一致，防止预热用默认参数而真正识图用页面参数。
- 删除识别预设前，固定保留当前明确选定的实际参数并处理旧配置，不擅自把用户 custom 参数重置为新的默认档。
